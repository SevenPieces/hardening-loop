# Worked example: a findings-driven run

Condensed from a real run, names and paths generalized. It shows the shape of
the loop, not a template to copy verbatim: the findings, the evidence and the
counts are the run's own.

## Invocation

```
hardening-loop target=skills/example-skill mode=findings-driven \
  findings=findings/2026-10-01.md refs=runs/2026-10-01/ baseline=v0.4.2 \
  branch=release/0.5
```

## Phase 0 - Reconnaissance

- Target is a documented skill: `SKILL.md` plus three `reference/` files and two scripts.
- Capabilities detected: methodology framework present (skill index available),
  delegation present, no production entry point (fallback: closest representative
  run in a scratch directory), delivered artifacts present (`runs/`, shipped
  outside the repository),
  reference artifacts provided, input findings provided, test runner present.
- Baseline `v0.4.2` still installs, so "no regression" means: the reference
  documents keep their meaning, the scripts keep their exit codes, and a fresh
  execution still produces a complete deliverable.

## Phase 1 - Goal

*Close every finding in `findings/2026-10-01.md`, re-audit the skill against
its own documented behavior, and leave no known finding at any severity -
including the process-compliance ones - with the `v0.4.2` behavior intact.*

Exit criteria as the checklist from `SKILL.md`, plus two run-specific ones:
the two scripts keep their documented exit codes, and the sample deliverable is
regenerated byte-identically by the documented commands.

## Phase 2 - Plan (abridged)

Skill usage plan: `verification-before-completion` for the Gate, the
methodology's review skill for the independent pass, and no skill skipped.
Delegation plan: the orchestrator holds implementation only. This run is too
small to split, so triage and regression merge into the independent verifier,
independent test design merges into verification, and the security/privacy scan
merges into the adversarial review; all four merges are recorded here with that
reason. One independent verifier (subagent) that never sees the implementation
notes, one adversarial reviewer (Phase 5).
Scope: the five input findings, and a re-audit of the whole target - `SKILL.md`,
the reference files and the two scripts - against its documented behaviour.

## Phase 3 - Triage (mode B)

| ID | Finding | Severity | Reproduction |
|---|---|---|---|
| F1 | Two reference files state different defaults for the same option | Medium | Both files read; delivered sample shows the losing value |
| F2 | A script exits 0 on a malformed argument | High | `script.mjs --broken` -> exit 0, no diagnostic |
| F3 | The coverage window ends at generation time, not run start | Medium | Not reproducible from the sample alone; mechanism located in the script |
| F4 | A worked example links to a renamed file | Trivial | Link target missing |
| F5 | The Gate could pass with an unrun verification step | Medium (process) | Read of the process text; no stop condition tied to the verification record |

F3 is marked *reproducible with instrumentation*: the script is run with a
patched clock, and the window end is shown to move with the clock. F5 is a
process-compliance finding that arrived in the input backlog, not one this run
raised: it is triaged here like any other input finding.

Mode B does not stop at the file: the mode A derivation follows. Reconnaissance
gaps and the adversarial hypothesis list - state-file contention under
concurrent execution, resumption after interruption, and documentation claims
that overstate behaviour - are added to the backlog. None of them is a separate
defect at triage time, so the five input findings remain the backlog's findings;
the derivation's candidates are carried into Phase 4 and the Phase 5 sweep,
which is what turns the concurrency and the "always" claim into findings.

## Phase 4 - Verification-action loop

**Baseline verification.** Before any change, the whole target is run against the
coverage matrix in `reference/coverage.md`: the five input findings reproduce as
recorded and nothing else appears, so the baseline is measured and clean apart
from the backlog.

### Round 1

The five input findings are one batch: no other defect has joined the backlog,
the run is too small to split them, and one verification step closes them
together. The derivation's candidates are not separate fixes: they are carried
into that same pass and into the Phase 5 sweep.

Actions: F1 changes one reference file to name the other as normative; F2 adds
an argument check and a non-zero exit; F3 records the run start and derives the
window end from it; F4 fixes the link; F5 adds a Gate line requiring the
verification record. F4 is a
documentation link with no behaviour to test - a link check closes it - and F5 is
a process gap closed by the Gate line it adds; those two are recorded as
justified rather than silently skipped.

Sensitive-information scan: the target, the diffs and the reference artifacts were scanned
for credentials and machine-specific values; one absolute path in a fixture was
replaced with the `$HOME`-relative form, and the replacement is named in the diff
so the sanitization can be checked.

Verification (against the same matrix): the independent verifier designs and
runs the regression tests for F1, F2 and F3 itself - they are not the
implementer's - then runs the scripts in a scratch directory outside the target,
twice in a row, and checks the delivered artifacts from the
baseline execution are byte-identical. **Finding V1 (Medium):** the second
execution of the script rewrites a state file it should only read, so the two
executions disagree -
a regression introduced by the F3 fix.

### Round 2

Action: the F3 fix now writes its derived state to the scratch path and leaves
the input state file untouched. A regression test asserts two consecutive
executions produce the same derived state.

Verification: clean - and Phase 5 still has to run before the Gate, so this is
not yet the last pass.

## Phase 5 - Adversarial sweep

Findings: a concurrent execution of the two scripts interleaves on the state file
(Medium); a documentation claim about "always" was false for the empty-input
case (Low); no privilege, injection or logging-hygiene issues found.

## Loop re-entry - Round 3

Both findings return to the action step. The state file gains a lock file and a
test for the concurrent case, and the "always" claim is reworded. The
verification step is clean.

## Phase 5 re-run - Adversarial sweep

The adversarial sweep runs again over the new state, because the fix is new
attack surface. This time it comes back clean: the lock file holds under a
concurrent run, and no new assumption fails.

## Phase 6 - Gate

The last finding is behind us and the adversarial sweep that followed it is
clean, so per the Gate rule one extra full verification step runs: the malformed-argument case, the consecutive-execution case,
the concurrent case and the sample regeneration. Clean again, so the Gate opens.

| Criterion | Result | Evidence |
|---|---|---|
| Input findings triaged, reproduced, fixed, regression-tested | Pass | Triage table; regression tests for F1, F2 and F3, a link check for F4, the Gate line for F5 |
| No known finding at any severity | Pass | Round 3 verification and the extra pass after it, both clean |
| No open item remains | Pass | Open item log is empty |
| Capability requirements met | Pass | Skill usage log, delegation log |
| Baseline holds | Pass | The pre-change behaviours re-run: the reference files read the same, the scripts keep their exit codes, and the sample still regenerates |
| Artifacts untouched, no leftovers | Pass | Scratch directory removed; `runs/` unchanged |
| The two scripts keep their documented exit codes | Pass | Both run to their documented codes in every verification pass |
| The sample deliverable is regenerated byte-identically | Pass | `v0.4.2` sample regenerated byte-identically by the documented command |

## Phase 7 - Completion

Commits merged locally on `release/0.5`, the branch the invocation named -
`main` when it names none - and nothing pushed. The report lists the exact push
command(s) and waits for approval. Read-only inputs are unmodified and uncommitted.

## What the loop actually caught

Three of the eight findings - V1, the concurrency issue, and the false "always" -
were invisible in the input findings: V1 surfaced when the verification step ran
again after a fix, and the other two turned into findings only under the
adversarial sweep. That is the loop's whole value: the second finding is usually
created by the fix for the first.
