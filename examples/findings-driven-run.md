# Worked example: a findings-driven run

Condensed from a real run, names and paths generalized. It shows the shape of
the loop, not a template to copy verbatim: the findings, the evidence and the
counts are the run's own.

## Invocation

```
hardening-loop target=skills/example-skill mode=findings-driven \
  findings=findings/2026-10-01.md refs=runs/2026-10-01/ baseline=v0.4.2 \
  branch=release/0.5
```

## Phase 0 - Reconnaissance

- Target is a documented skill: `SKILL.md` plus three `reference/` files and two scripts.
- Capabilities detected: methodology framework present (skill index available),
  delegation present, production mode present (the documented sample-regeneration
  command is the entry point, and its real inputs are the shipped sample inputs),
  goal tracking present (goal armed in Phase 1, id recorded), delivered artifacts
  present (`runs/`, shipped outside the repository), reference artifacts
  provided, input findings provided, test runner present. This is the full set of
  eight - the declaration table in the run's report carries one evidence row for
  each; the production row carries the command and its inputs, not the word
  `present`.
- Baseline `v0.4.2` still installs, so "no regression" means: the reference
  documents keep their meaning, the scripts keep their exit codes, and a fresh
  execution still produces a complete deliverable.

## Phase 1 - Goal

*Close every finding in `findings/2026-10-01.md`, re-audit the skill against
its own documented behavior, and leave no known finding at any severity -
including the process-compliance ones - with the `v0.4.2` behavior intact.*

The harness goal is armed with that objective as `goal:hardening-0.5`, and the
declaration records the id. The goal stays active until the Gate opens - every
round below re-checks that it is still open. This run satisfies the Gate, so the
goal is closed as achieved after the Gate's extra pass and the goal check both
pass, and the report records that closing state and that it came before the
merge.

Exit criteria as the checklist from `SKILL.md`, plus two run-specific ones:
the two scripts keep their documented exit codes, and the sample deliverable is
regenerated byte-identically by the documented commands.

## Phase 2 - Plan (abridged)

Skill usage plan: `verification-before-completion` for the Gate, the
methodology's review skill for the independent pass, and no skill skipped.
Delegation plan: seven roles are staffed by seven agents: implementation,
verification, independent test design, adversarial review, triage, the
security/privacy scan, and regression/cross-effects. No agent holds two roles;
the orchestrator holds none. Each role runs in a fresh agent of its own, and the
verifier and the adversary never see the implementation notes. A small run is a
reason to say what each agent did, not to merge roles: any role this run could not
staff separately would be recorded as a degradation with a Gate compliance
finding, never merged. None is recorded here, because all seven were staffed
separately.
Scope: the five input findings, and a re-audit of the whole target - `SKILL.md`,
the reference files and the two scripts - against its documented behaviour.

## Phase 3 - Triage (mode B)

| ID | Finding | Severity | Reproduction |
|---|---|---|---|
| 1 | Two reference files state different defaults for the same option | Medium | Both files read; delivered sample shows the losing value |
| 2 | A script exits 0 on a malformed argument | High | `script.mjs --broken` -> exit 0, no diagnostic |
| 3 | The coverage window ends at generation time, not run start | Medium | Not reproducible from the sample alone; mechanism located in the script |
| 4 | A worked example links to a renamed file | Trivial | Link target missing |
| 5 | The Gate could pass with an unrun verification step | Medium (process) | Read of the process text; no stop condition tied to the verification record |

The IDs are one sequence for the whole report, as
`reference/report-template.md` requires: no per-source prefixes. This table and
the §9 finding log share the sequence, and an item that moves between them keeps
its ID - which is why the regression found in Round 1 is 6, not `V1`, and the
two sweep findings are 7 and 8.

Finding 3 is marked *reproducible with instrumentation*: the script is run with a
patched clock, and the window end is shown to move with the clock. Finding 5 is a
process-compliance finding that arrived in the input backlog, not one this run
raised: it is triaged here like any other input finding.

Mode B does not stop at the file: the mode A derivation follows. Reconnaissance
gaps and the adversarial hypothesis list - state-file contention under
concurrent execution, resumption after interruption, and documentation claims
that overstate behaviour - are added to the backlog. None of them is a separate
defect at triage time, so the five input findings remain the backlog's findings;
the derivation's candidates are carried into Phase 4 and the Phase 5 sweep,
which is what turns the concurrency and the "always" claim into findings.

## Phase 4 - Verification-action loop

**Baseline verification.** Before any change, the whole target is run against the
coverage matrix in `reference/coverage.md`: the five input findings reproduce as
recorded and nothing else appears, so the baseline is measured and clean apart
from the backlog.

### Round 1

The five input findings are one batch: no other defect has joined the backlog,
the run is too small to split them, and one verification step closes them
together. The derivation's candidates are not separate fixes: they are carried
into that same pass and into the Phase 5 sweep.

Actions: finding 1 changes one reference file to name the other as normative;
finding 2 adds an argument check and a non-zero exit; finding 3 records the run
start and derives the window end from it; finding 4 fixes the link; finding 5
adds a Gate line requiring the verification record. Finding 4 is a documentation
link with no behaviour to test - a link check closes it - and finding 5 is a
process gap closed by the Gate line it adds; those two are recorded as justified
rather than silently skipped. The security/privacy agent scans the target, the
diffs and the reference artifacts for credentials and machine-specific values;
one absolute path in a fixture is replaced with the `$HOME`-relative form, and
the replacement is named in the diff so the sanitization can be checked.

The action step closed the batch as commit `a1c9f02`; the close-of-batch gate took
`a1c9f02` - the tree was clean and no implementation was still running - and
the verification step, the sweep and the finding log all report against it.

Verification (against the same matrix and the same revision): the independent
test-design agent writes the regression tests for findings 1, 2 and 3, and the
verification agent runs them - designed and run by agents that did not implement
them. The verifier then runs the scripts in a scratch directory outside the
target, twice in a row, and runs the declared production-mode workload - the
documented sample-regeneration command, on the shipped sample inputs - in that
scratch directory; the delivered artifacts from the baseline execution are
byte-identical. **Finding 6 (Medium):** the second execution of the script
rewrites a state file it should only read, so the two executions disagree - a
regression introduced by the finding-3 fix.

### Round 2

Action: the finding-3 fix now writes its derived state to the scratch path and
leaves the input state file untouched. A regression test asserts two consecutive
executions produce the same derived state. The step closes the batch as commit
`b7e4410`; the close-of-batch gate took `b7e4410`, and verification reports
against it, clean - and Phase 5 still has to run before the Gate, so this is not
yet the last pass. The security/privacy agent re-scans the new diff and records
nothing found.

### Close-of-batch gate, exercised

When Round 1's batch was first handed over it was not clean - the link fix for
finding 4 was still uncommitted - so the close-of-batch gate did not pass. It did
not start verification: it returned the round to the action step, which finished
the commit as `a1c9f02`, and the gate took that revision on the retry. That
return is the gate working, not a finding: verifying the half-committed tree
would have produced evidence for a revision that never existed.

## Phase 5 - Adversarial sweep

The sweep attacks `b7e4410`, the revision the Round-2 verification reported
clean, and reports every finding against it. Findings: a concurrent execution of
the two scripts interleaves on the state file (Medium, finding 7); a
documentation claim about "always" was false for the empty-input case (Low,
finding 8); no privilege, injection or logging-hygiene issues found.

## Loop re-entry - Round 3

Both findings return to the action step. The state file gains a lock file and a
test for the concurrent case, and the "always" claim is reworded. The step closes
the batch as commit `d4f0a15`; the close-of-batch gate took `d4f0a15` and the
verification step is clean. The security/privacy agent re-scans the new diff and
records nothing found.

## Phase 5 re-run - Adversarial sweep

The adversarial sweep runs again, because the fix is new attack surface: it
attacks `d4f0a15`, the revision the Round-3 verification reported clean. This
time it comes back clean: the lock file holds under a concurrent run, and no new
assumption fails.

## Phase 6 - Gate

The last finding is behind us and the adversarial sweep that followed it is
clean, so per the Gate rule one extra full verification step runs over the final
revision `d4f0a15`: the malformed-argument case, the consecutive-execution case,
the concurrent case and the sample regeneration. Clean again, so the Gate opens -
and only that revision is what Phase 7 merges.

| Criterion | Result | Evidence |
|---|---|---|
| Input findings triaged, reproduced, fixed, regression-tested | Pass | Triage table; regression tests for findings 1, 2 and 3, a link check for finding 4, the Gate line for finding 5 |
| No known finding at any severity | Pass | Round 3 verification, the sweep re-run and the extra pass after them, all clean over `d4f0a15` |
| No open item remains | Pass | Open item log is empty |
| Capability requirements met | Pass | Skill usage log, delegation log |
| Baseline holds | Pass | The pre-change behaviours re-run: the reference files read the same, the scripts keep their exit codes, and the sample still regenerates |
| Artifacts untouched, no leftovers | Pass | Scratch directory removed; `runs/` unchanged |
| The two scripts keep their documented exit codes | Pass | Both run to their documented codes in every verification pass |
| The sample deliverable is regenerated byte-identically | Pass | `v0.4.2` sample regenerated byte-identically by the documented command |

## Phase 7 - Completion

The revision the Gate approved - `d4f0a15`, the one the extra pass verified - is
merged locally on `release/0.5`, the branch the invocation named, and nothing is
pushed; anything landing after that pass re-enters the loop rather than riding
along. The report lists the exact push command(s) and waits for approval.
Read-only inputs are unmodified and uncommitted.

## What the loop actually caught

Three of the eight findings - 6, the concurrency issue, and the false "always" -
were invisible in the input findings: finding 6 surfaced when the verification
step ran again after a fix, and the other two turned into findings only under the
adversarial sweep. That is the loop's whole value: the second finding is usually
created by the fix for the first.
